## Alcance de una política y procedencia de la selección

Las dos solicitudes de la sonda 1 llegaron con `config.cwd = <sandbox>/fixtures/<run>/clone` y los marcadores de metadata distintos enviados por cada cliente. `workspace.create.after` registró un mismo `projectId` para ambos IDs y las dos sesiones quedaron en los workspaces que seleccionó el cliente. El cambio de `workspaceId` que propuso el segundo plugin se rechazó en tiempo de ejecución. El validador exige conservar el valor, aunque la firma del hook permite devolver la propiedad. La sonda construyó dos tuplas distintas con `api.hosts.list().self.serverId` y `api.workspaces.ref(id).refresh()`. La validación de la tupla determina el alcance de la solicitud. La procedencia de la autorización requiere un control independiente.

Las comparaciones de modelo controlaron la selección explícita del mismo modelo que el proveedor elegiría por defecto. La traza registró `config`, `metadata`, `workspaceId` y los nombres de las variables de entorno en `agent.create.before`. El contexto expuso `paseo` y `signal`. En `agent.open.before` se compararon `workspaceId`, proveedor, cwd, motivo, propósito, título, modo background, etiquetas, metadata, nombres de variables y servidores MCP, y cantidad de herramientas. Se excluyó el ID único de cada agente de esa comparación. CLI y cliente SDK de bajo nivel dejaron `config.model` ausente al omitirlo. La distinción de esos clientes se reduce a la presencia del valor en la solicitud. En el SDK de alto nivel, `api.agents.create` rechazó una configuración con solo el proveedor y aceptó el destino explícito.

En Chrome headless se eligió `Fixture default` en el primer borrador y se envió un turno sintético. El segundo borrador mostró el mismo modelo. Se envió el mismo texto sin tocar el selector del segundo borrador. Los payloads capturados de ambos hooks coincidieron campo por campo tras excluir el ID único del agente. Los dos enviaron `model: "fixture-default"` y `modeId: "fixture-mode"`, el mismo workspace y cwd, metadata y etiquetas vacías, y ninguna diferencia de opciones, thinking, entorno o herramientas. El bundle de `@getpaseo/server/dist/server/web-ui/_expo/static/js/web` construye el payload de New Agent desde `effectiveModelId` por medio de `buildWorkspaceDraftAgentConfig`. Falta una procedencia verificable de la selección cuando el compositor ya conoce el modelo efectivo.

## Relevo y retirada

Los schedules de una ejecución completaron cada run por separado. El heartbeat dirigido al agente existente se ejecutó vía `scheduleCreate` con `target.type = "agent"` y `scheduleRunOnce`. Reutilizó el ID del agente y conservó su workspace. Su salida arrastró el fallo sintético previo pese al estado `succeeded`. El estado del schedule no acredita una transición de autoridad ni el resultado semántico del turno.

El CLI y el cliente ofrecen `agent detach` y `detachAgent`. La implementación incluida quita el vínculo de parentesco en las etiquetas. El servicio de schedules serializa por ID de schedule dentro del daemon y concilia runs interrumpidos al arrancar. En los contratos de CLI, cliente y plugins inspeccionados no se encontró una operación que reconcilie checkpoint, cesión explícita y adquisición exclusiva con época ni que invalide efectos de la época saliente. La prueba SQLite de Zelqio verifica un mecanismo independiente en una fila sintética. La condición de transferencia automática de [Relevo de coordinación](../../planning/DEVELOPMENT-WORKFLOW.md#relevo-de-coordinación) sigue sin cubrirse.

Se repitió [POC-08](S00-T05-subagents-worktrees.md#poc-08) con el mismo estado de Git observable, archivos tracked modificados y untracked, en ramas nuevas del remoto local bare. El hook de teardown se probó sobre un comando configurado en `paseo.json`. La implementación publica `workspace.archive.after` al archivar el registro y continúa hacia la retirada del checkout. La sonda vio esa ventana, pero el evento no espera la decisión del plugin. El contrato ofrece además un administrador de worktrees para checkouts que el plugin administra. Sus usos quedan fuera de esta sonda sobre el checkout nativo.

El cliente web nativo mostró `Archive 2 workspaces?` y un aviso de cambios sin confirmar para cada checkout. El driver respondió afirmativamente a ese diálogo específico de los dos fixtures. Desaparecieron ambos directorios y la traza registró un `git worktree remove <path> --force` para cada uno.

## Reproducción

El runner requiere Windows, un directorio `<sandbox>` ya preparado con `v0.17.5/node_modules`, puertos libres de la prueba y nombres `run-*` nuevos. Usar un runner a la vez. La fase de compatibilidad también necesita una copia física de las dependencias del repositorio en `node_modules`. Cada fase comprueba los listeners antes y después y detiene su daemon en `finally`. Para la fase web se usó Chrome 158.0.8127.37 con perfil nuevo. El servidor local de prueba en `127.0.0.1:16776` sirve el bundle incluido en Paseo y añade el script de interacción. La política CSP del servidor acota las conexiones y bloquea el intento automático del cliente web hacia el puerto habitual. Conservar los logs de los homes desechables para inspección local.

```powershell
$Sandbox = '<sandbox>'
$GitExe = (Get-Command git.exe).Source
$NodeDir = Split-Path (Get-Command node.exe).Source
$NpmCli = Join-Path $NodeDir 'node_modules/npm/bin/npm-cli.js'
$ChromeExe = '<chrome.exe>'
$Run = 'poc/paseo-0.17.5/run.mjs'
$Suffix = Get-Date -Format 'yyyyMMdd-HHmmss'
node $Run $Sandbox "run-bootstrap-$Suffix" $GitExe
node $Run $Sandbox "run-sessions-$Suffix" $GitExe sessions
node $Run $Sandbox "run-retirement-$Suffix" $GitExe retirement
node $Run $Sandbox "run-browser-$Suffix" $GitExe browser $ChromeExe
node $Run $Sandbox "run-compatibility-$Suffix" $GitExe compatibility $NpmCli (Get-Location).Path
npm run check
```

CLI, daemon, SDK instalado y proveedor de protocolo se probaron sobre Paseo 0.17.5, con Node.js 24.21.0, npm 11.19.0 y Git 2.50.1.windows.1. Se observaron exclusivamente directorios y sesiones de prueba. El proveedor `zelqio-fixture` responde localmente con eventos sintéticos. **Presupuesto real de inferencia: 0 prompts, 0 proveedores externos.** El worktree de evidencia, con sus dependencias fijadas, pasó `npm run check` con 383 pruebas en 33 archivos.
